### Шаг 14: Ошибка «null value in column variant_id» — вся механика заказа (2026-11-07, ветка arena/cc8372d9-shop)
- Баг владельца из боевой базы: добавление товара в корзину падало с `null value in column "variant_id" of relation "cart_items" violates not-null constraint`.
- Причина: `PRIMARY KEY (tg_user_id, product_id, variant_id)`. В PostgreSQL колонка первичного ключа **неявно NOT NULL**, поэтому товар без вариантов (у нас таких 11 из 17) не вставлялся вовсе. На SQLite NULL в PK разрешён — локально всё работало, поэтому баг жил долго.
- Решение: `cart_items.id TEXT PRIMARY KEY`, уникальность пары держит `idx_cart_unique (tg_user_id, product_id, COALESCE(variant_id,''))`. Новая схема — во всех трёх DDL (db-setup.sql, db-postgres-schema.ts, db-sqlite.ts).
- ВАЖНО, грабли: **удаление первичного ключа НЕ снимает неявный NOT NULL** с его колонок — нужен отдельный `ALTER COLUMN variant_id DROP NOT NULL`. На этом проверка падала, пока не добавил явный DROP NOT NULL.
- Миграция: `migrateCartTable()` в db-postgres-schema.ts (обычные запросы, не DO-блок) + пересоздание таблицы в `migrateSqlite`. Проверено на базе со старым ключом: строки и количества сохраняются.
- Вторая найденная проблема: `ensurePostgresSchema` кэшировал промис в модульной переменной — в одном процессе вторая база оставалась БЕЗ схемы. Теперь `WeakMap<Db, Promise>`.
- PGlite не разбирает dollar-quoting с тегом (`$body$`) и DO-блоки в exec — миграции в TS, а не в SQL.
- Проверки: `check:pg` — новый `checkOrderFlow()` (корзина с вариантом/без, количества, чужой вариант, оформление, позиции, кешбэк, статусы, очистка) и `checkCartMigration()` (воспроизводит старую ошибку, гоняет настоящий ensurePostgresSchema, проверяет идемпотентность). `check:shop` — 3 ассерта на id строки корзины.
- Живой прогон по HTTP: PS5 без варианта + iPhone с вариантом → корзина 199 970 ₽, выгода 40 000 ₽ → заказ с 2 позициями, корзина очищена.
- Вторая дыра, найденная при прогоне механики: можно было оформить заказ на товар, снятый с продажи (10 позиций каталога скрываются владельцем). Теперь: `addToCart` требует `is_active = true`; `getCart` присоединяет только активные товары (JOIN ... AND p.is_active); `createPurchaseOrder` при снятой позиции бросает «Часть товаров больше не продаётся — обновите корзину» — молча урезать заказ нельзя, клиент подтверждал другую сумму; сумма заказа считается на сервере по актуальным ценам, а не из присланного `total`.
- Побочный эффект: `createPurchaseOrder` больше не верит `input.total` → `check:shop` передавал выдуманные 100 000 — тест переписан на реальную цену. `check:bot` брал `listProductsAdmin()[0]` и мог взять скрытый товар — теперь `.find(p => p.isActive)`.

### Шаг 10: Очереди, приём оплаты, поиск заказа, массовые действия (2026-11-05)
- Контекст: владелец просил четыре вещи «плюс логику и оформление, чтобы было интуитивно понятно»: реквизиты/ссылка оплаты клиенту, главный экран со счётчиками, поиск заказа и телефон в один тап, массовые действия по категориям.
- Решение: `settings` (key/value) в SQLite и PostgreSQL — реквизиты правятся из бота без деплоя. Главный экран отвечает на «что делать сейчас»: три очереди кнопками со счётчиками, при пустоте «Срочных дел нет», при ненастроенной оплате — предупреждение. Реквизиты подставляются в уведомление «заказ подтверждён»; без настроек клиенту честно предлагается написать менеджеру. Поиск — по хвосту номера, телефону и имени. Массовые: `bulkSetActive` и `bulkReprice` (процент, округление до рубля, минимум 1 ₽, надбавки вариантов не трогаются).
- Альтернативы: реквизиты в env — отклонено (правка требует пересборки и рестарта); таблица на каждую настройку — отклонено (key/value дешевле, список ключей в `SETTING_DEFS`); изменение цен на фиксированную сумму — отклонено (владелец мыслит процентами).
- Риски: настройки уходят клиенту, секреты туда класть нельзя; процент считается от округлённой цены, поэтому «+10%, затем −10%» даёт расхождение до 1 %; массовое скрытие не трогает заказы и корзины (товар может исчезнуть из уже собранной корзины).
- Найденные баги: (1) `\u0000` в параметре SQLite обрезается драйвером, и `LIKE '%%'` совпадал со всеми заказами — теперь `(? <> '')` + `ESCAPE '\'`; (2) проценты давали цены с копейками (39 590,10 ₽) — округление до рубля; (3) подсказка «пустое сообщение стирает» не совпадала с поведением (стирает `-`); (4) голый callback `bulk` после удаления дубликата терял рендер экрана — починено отдельной ветвью `if (!arg)` с тестом и смоуком.

### Шаг 8: Полноценная панель в боте — товары, варианты, характеристики, бонусы (2026-11-05)
- Контекст: владелец должен управлять магазином целиком из Telegram: выставлять товар, грузить фото, менять цены, статусы заказов. До этого бот умел только три поля товара и заявки.
- Решение: логика разделена на три слоя — `bot-input.ts` (разбор ввода: цена, варианты, характеристики, телефон, id), `bot-admin-flow.ts` (действия с данными: черновик товара, создание, правка полей, варианты, спеки, обложка, галерея, бонусы, комментарий к заказу), `bot-screens-admin.ts` (экраны панели). Вебхук только разбирает апдейт и отправляет сообщения. Черновик нового товара живёт в `bot_state` как JSON — переживает холодный старт без новой таблицы. Ввод не требует нажимать поле: текст заполняет первое пустое обязательное поле. Фото из чата идёт в обложку, галерею или черновик в зависимости от сессии; без S3 бот честно объясняет, что хранилище не настроено.
- Альтернативы: отдельная таблица `drafts` — отклонено (одна колонка JSON в существующей `bot_state` дешевле и так же переживает рестарт); мастер с обязательными кнопками на каждом шаге — отклонено (в чате естественнее просто отвечать текстом); загрузка видео файлом через вебхук — отклонено (лимит Bot API 20 МБ, файл не переживёт таймаут; принимаем ссылку на mp4); удаление товара без подтверждения — отклонено (необратимо, поэтому экран подтверждения с предложением скрыть).
- Риски: удаление товара чистит варианты/спеки/медиа/корзину, но не историю заказов — это осознанно; `bot_state` одноразовый, поэтому после ошибки шаг переустанавливается, иначе владелец застрял бы; бонусы при отмене возвращаются, а кешбэк снимается только в пределах остатка.
- Найденные и исправленные баги: (1) `parsePriceRub("12a")` возвращал 12 ₽ — теперь буквы и дроби отклоняются; (2) `LOWER()` в SQLite не понимает кириллицу — поиск товаров и категорий по-русски не находил ничего, сравнение перенесено в JS; (3) `prod()` в repo не читал `brand` — бренд записывался, но не возвращался; (4) кешбэк за заказ терялся, если профиль клиента ещё не создан — теперь `addBonus` создаёт строку лениво; (5) текст на шаге черновика игнорировался (после `/new` название пропадало) — добавлен `applyDraftText`; (6) `parseVariantLine` принимал «??» как название варианта.
- Проверка: `check:bot` — 120 утверждений (доступ, экраны, разбор ввода, черновик, создание товара, категории, варианты с надбавками, характеристики с единицами, обложка и видео, удаление, бонусы и отмена заказа); `check:shop` 52, `check:pg`, `check:storage`, `lint` 0, `typecheck`, `build`; dev + curl: `/api/bot/webhook` без секрета 503, с секретом 200 на `/start`, `/new`, названии и цене — черновик в `bot_state` накапливает поля.

### Шаг 7: Витрина магазина — фильтры, варианты, корзина, кабинет (2026-11-05)
- Контекст: спецификация магазина техники: сложная фильтрация и сортировка, карусель фото, табы «описание / характеристики / отзывы», конфигурации с динамической ценой, «с этим покупают», корзина с автопересчётом и удалением свайпом, оформление в 1–2 клика с данными из Telegram, кабинет с бонусами/рефералом/историей и статусами доставки, которые меняет админ в боте, сравнение 2–3 товаров, haptic и микроанимации.
- Решение: данные — схема v0004 (10 новых таблиц: варианты, спеки, медиа, отзывы, избранное, корзина, покупатели, бонусный журнал, позиции заказа, события заказа). Логика разделена по ответственности: `catalog.ts` (фильтры, фасеты, деталь, сравнение, избранное), `shop.ts` (профиль, бонусы, корзина, заказы, доставка), `reviews.ts`, `api-user.ts`. UI — `src/components/shop/*` с навигацией в состоянии (`ShopApp`), потому что роутер перезагружал бы корзину и терял выбранные варианты. Статусы доставки хранятся в `orders.delivery_status`, каждое изменение — в `order_events`; бот меняет их кнопками `delivery:<orderId>:<status>` и принимает трек-номер через сессию `bot_state`.
- Альтернативы: Zustand/Redux для корзины — отклонено (источник правды всё равно сервер, каждая мутация возвращает корзину; локальный стор дублировал бы суммы и расходился); отдельные роуты `/product/[id]`, `/cart` — отклонено (в Mini App переходы с перезагрузкой заметны, а состояние сравнения и фильтров терялось бы); весовые коэффициенты для «лучше» в сравнении — отклонено (пользователь ждёт объективных цифр, поэтому подсвечиваются только память, камера, автономность, частота).
- Риски: фасеты считаются в памяти по всем товарам — до сотен позиций это дешевле сложного SQL, дальше нужен индекс; `product_specs` используется и для характеристик, и для cross-sell (`group_name='cross-sell'`) — при выборках обязателен фильтр по группе.

- Найденный баг: сид пропускал существующие товары, поэтому на проде после обновления схемы не появились бы ни бренды, ни варианты. Теперь `seedDetails` работает как синхронизация по стабильному ключу (`kind+label` для вариантов, `group+name` для спек): недостающее создаёт, изменённое обновляет на месте (id вариантов сохраняются — корзины клиентов не ломаются), галерею только досоздаёт, цену и фото товара не трогает. `seedIfEnabled` включён по умолчанию, `AUTO_SEED=0` отключает.
- Найдено при прогоне на живой базе: фасеты смешивали «Мощность всасывания» в Вт и Па (пылесос против робота), а единица бралась «какая попалась» — числовые фильтры показывались без единицы. Ключ фасета теперь «имя + unit», в сиде разведены аВт/Па и добавлены единицы. Видео в галерее различается по `kind` — карточка вставляет плеер. Порядок товаров в боте получил добивку по `title`: при одинаковом `created_at` (точность до секунды) страница скакала, и `check:bot` флапал.
